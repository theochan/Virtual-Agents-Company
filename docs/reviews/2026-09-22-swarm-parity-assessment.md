# VAC versus Grok Bot and Kimi Swarm — 22 September 2026

**Decision: not on par.** VAC is a bounded local swarm implementation with narrow live development successes. It does not yet demonstrate comparable autonomous usefulness, app coverage, multimodal handling, availability or scale. This is a capability/evidence audit, not a measured head-to-head product benchmark. Vendor documentation describes advertised behavior; it does not prove vendors always succeed.

The central mistake would be equating tool count, a task tree or agent headcount with reliable completed work. The next investment should be correct, independently judged outcomes and less owner correction time. Scale is secondary until a small swarm beats one equipped agent on relevant work.

## Priority and acceptance

1. **Prove correctness and value:** VAC-23, VAC-28 and VAC-42. Freeze candidate and rubric before new runs; finish a useful full workflow, three fresh repetitions and a separately authored holdout. Record every failure. Begin benchmark design now; do not wait for distributed infrastructure.
2. **Complete a narrow real-app path:** VAC-24–27 and VAC-38. Select actual apps and authorized test accounts; verify outcomes in those apps. Add VAC-43/44 for document-heavy work. A tool receipt alone does not prove a useful deliverable.
3. **Make successful work reusable:** VAC-39 memory retrieval, VAC-45 skill authoring and VAC-46 triggers, then VAC-29 availability and VAC-32 long-horizon observation. No subscriptions or unattended jobs are activated by creating these items.
4. **Scale only after benefit is demonstrated:** VAC-31/33; enterprise identity and native platforms as explicit product scope. Local capacity/storage baselines can start now; distributed dependencies apply to distributed acceptance, not basic measurement.
